# Samskill 原子库与标准完整度审计

审计日期：2026-08-13  
审计对象：`Samskill 1.0.0-beta.3` GitHub 公开测试包

## 先说结论

当前公开包已经是一套**能够安装、能够路由、能够按专项任务运行的 Beta 运行包**。

但它还不是一套“完整公开原子库 + 完整运行标准 + 完整验证样例”的稳定开源发行版。

准确地说：

- **18 个 Skill 的运行骨架：完整。**
- **每个 Skill 的输入卡与输出模板：完整。**
- **专项运行所需的裁剪参考资料：基本完整。**
- **叁木完整原子库：没有完整收入开源包。**
- **跨模块统一标准：部分已经编译进各 Skill，但没有作为唯一真源完整公开。**
- **真实金标准交付样例：不完整。**
- **真实项目前向验证：仍在进行。**

因此，当前最准确的名称是：

> Samskill 可运行开源候选版，而不是完整知识源稳定版。

## 一｜审计对象不是同一个版本

### GitHub 公开测试包

它指的是从 GitHub 克隆或下载后看到的公开测试包。

它包含本轮新增的输入卡、输出合同、安装器、测试和开源文档。

### 当前已安装运行版

它指的是 Agent 实际读取的 Skills 安装目录，例如 `~/.codex/skills/`。

安装后的实际版本以 `python3 scripts/verify_install.py --target <skills目录>` 输出为准。

## 二｜开源包实际包含了什么

### 运行结构

| 项目 | 结果 |
|---|---:|
| Skill 总数 | 18 |
| 总入口 | 1 |
| 专项 Skill | 17 |
| 输入卡 | 18/18 |
| 输出模板 | 18/18 |
| 安装／校验／卸载脚本 | 已包含 |
| 任务触发与压力测试 | 已包含 |
| 参考资料文件 | 461 份 |
| 去重后的参考资料 | 246 份 |

参考资料数量大于去重数量，是因为同一份运行标准会被复制到多个必须独立运行的 Skill 中。

这不是内容越多越好，而是当前采用了“每个 Skill 自包含”的安装方式。

### 已经编译进 Skill 的资料类型

- 17 个模块的运行入口与说明材料。
- 工具、判断表和执行合同。
- 模块案例、边界、来源映射与测试。
- 写作标准、内容框架、形式选择、内容质检和原创重构协议。
- 人群市场深描与账号对标深拆合同。

这些资料足以支持 Beta 运行。

## 三｜完整原子库有没有被收入开源包

### 完整原子库现状

当前另有一套“叁木完整原子库 V2.0 Skill-ready 成熟候选版”作为内部知识真源。

它包含：

- 17/17 个模块。
- 203/203 张原子卡。
- 79 张来源与证据卡。
- 17 份模块案例。
- 模块运行入口、工具、边界和验收资料。
- 跨模块冲突、证据、输入输出、时效与渐进加载协议。

它的状态是“Skill-ready 成熟候选”，不是“已经被市场完全验证”。

### 开源包与完整原子库的差异

| 项目 | 完整原子库 | 当前开源包 |
|---|---:|---:|
| 原始文件总量 | 540 | 未完整收入 |
| 精确收入的唯一原始文件 | 540 | 156 |
| 原子卡 `SAM-*` | 203 | 0 |
| 来源证据卡 `SRC-*` | 79 | 0 |
| 运行时裁剪参考资料 | 有 | 有 |
| 适合 Agent 渐进加载 | 是 | 是 |
| 适合外部审核理论来源 | 是 | 目前不足 |

结论：

> 当前包收入的是“从原子库编译出来的运行子集”，不是完整原子库本体。

这并不会直接导致 Skill 无法运行。

但会影响三件事：

1. 外部用户无法完整检查每条判断来自哪里。
2. 开发者难以基于原子卡贡献、修订和追踪版本。
3. 当运行结果出现冲突时，缺少公开的知识真源进行仲裁。

## 四｜为什么不能把完整原子库直接塞进每个 Skill

Agent Skill 应该采用渐进加载。

运行时只读取当前任务需要的材料，不能每次把 540 份文件全部放进上下文。

所以正确的开源结构不是把完整原子库复制 18 遍，而是分成两层：

```text
Samskill/
├── skills/            # 可独立安装的运行子库
├── knowledge-base/    # 可审核、可贡献的公开原子库唯一真源
├── standards/         # 跨模块统一标准与协议
├── examples/          # 每个 Skill 的完整脱敏样例
├── docs/
├── scripts/
└── tests/
```

`skills/` 负责运行。

`knowledge-base/` 负责解释、复用、贡献和追溯。

`standards/` 负责解决不同 Skill 之间的冲突与一致性。

## 五｜为什么内部完整原子库不直接公开

内部完整原子库包含研发过程、客户项目与尚未统一授权格式的材料。

公开仓库只收入完成净化、当前运行需要且能说明判断边界的子集。

这不代表这些内容不能使用。

它意味着：

> 公开运行库与内部研发库必须分层，不能把内部知识资产原样打包出去。

## 六｜标准是否完整

需要把“标准”分成三类判断。

### A. 单个 Skill 的运行标准

**结论：Beta 级别基本完整。**

当前已有：

- 18/18 输入卡。
- 18/18 输出模板。
- 16 份专项运行合同。
- 16 份公开输入输出合同。
- 16 份压力测试。
- 16 份来源映射。
- 写作标准、内容框架选择、形式选择、质量审计和重构标准。
- 人群深描与对标深拆标准。

不足在于：

- 有些输出模板已经达到详细交付颗粒度，例如 `sam-position` 与 `sam-benchmark`。
- 其余模板更多是“完整骨架”，详细判断规则分散在 `SKILL.md` 和 `references/` 中。
- 外部用户可以运行，但不容易一眼看见每个结论是按什么标准得出的。

### B. 跨 Skill 的统一标准

**结论：规则存在，但公开包内没有形成唯一真源。**

完整原子库已有以下协议：

1. Skill-ready 验收标准。
2. 原子库到 Samskill 的运行协议。
3. 跨模块冲突与优先级协议。
4. 案例证据协议与案例索引。
5. 工具合同总索引。
6. 标准输入输出与失败样本索引。
7. 时效与版本更新协议。
8. 引用与渐进加载协议。

当前开源包把其中一部分规则编译进了各 Skill，却没有建立根目录 `standards/` 作为公开唯一真源。

这会带来重复和版本漂移风险。

### C. 结果质量与真实验证标准

**结论：还不完整。**

目前只有 4 份公开交付示例，而且主要用于展示结构，不足以代表 18 个 Skill 的完整金标准。

稳定公开版至少需要：

- 18 个 Skill 各 1 份完整、脱敏、可复查的输入与输出样例。
- 每份样例说明判断依据、用户确认点和真实执行结果。
- 至少 3 个不同项目完成端到端前向测试。
- 平台规则类判断带官方来源与更新时间。
- 失败样例和降级策略真正跑通，而不是只写在文档里。

## 七｜当前成熟度判定

### 已达到

- 一个总入口和 17 个专项 Skill 已经形成清晰分工。
- 安装器、备份、冲突处理、校验、卸载和测试框架已经建立。
- 输入不再要求用户一次性填完大问卷。
- 输出不再默认暴露内部 YAML 和状态字段。
- 写作、修改、审计、重构、人群和对标等核心链路已有专项标准。
- 运行包能够作为真实项目测试版使用。

### 尚未达到

- 完整公开原子库。
- 根目录统一标准库。
- 18/18 金标准完整交付样例。
- 完整来源、授权和案例公开审计。
- 多项目稳定前向验证。

## 八｜发布建议

### 现在可以发布为什么版本

可以发布：

> `1.0.0-beta.2` 公开测试版。

前提是 README 明确说明：

- 这是可运行测试版。
- 完整公开原子库仍在整理。
- 测试集存在不等于效果已经被证明。
- 建议先在副本或非关键项目中测试。

### 什么时候可以叫稳定开源 V1

P0 必须完成：

1. 生成去路径、去内部比较、完成案例脱敏的公开原子库。
2. 建立根目录 `standards/`，形成跨 Skill 唯一真源。
3. 为 18 个 Skill 各补一份完整脱敏交付样例。
4. 建立“原子卡 → 运行参考 → Skill → 输出字段”的追踪清单。
5. 完成来源、引用、许可证和案例授权审计。

P1 建议完成：

1. 用三个真实项目完成端到端测试。
2. 记录失败、回退和再次运行结果。
3. 建立平台规则的版本更新机制。
4. 根据外部用户的理解成本修订输入卡和输出说明。

## 九｜最终判断

如果问题是：

> 现在能不能安装试用？

答案是：可以，作为 Beta 测试版。

如果问题是：

> 现在这个包是否已经完整包含叁木原子库？

答案是：没有。

如果问题是：

> 当前标准是否足以开始真实项目测试？

答案是：足以。

如果问题是：

> 当前标准是否足以称为完整、稳定、可复查的开源 V1？

答案是：还不够。

下一步不应该继续增加更多 Skill。

应该补齐公开原子库、统一标准真源和 18 份金标准交付样例。

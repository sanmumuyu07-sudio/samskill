# 叁木输入、判断与交付协议 V2.2

本协议是所有 Samskill 任务 Skill 的共用运行底座。

它解决三个问题：

1. 用户说得乱、信息少或前后冲突时，怎样继续工作。
2. 哪些信息可以暂定，哪些事实必须由用户确认。
3. 同一个判断怎样分别交付给本人、团队、客户和项目档案。

专项 Skill 仍负责自己的专业判断。

本协议不替代专项方法、标准或输出字段。

---

## 一、启动顺序

每次运行先完成以下动作：

1. 读取本轮对话。
2. 读取用户点名的文件、链接、图片或数据。
3. 读取已有项目状态、最近结论和有效交接包。
4. 识别本轮任务。
5. 识别交付对象和交付形态。
6. 把输入标记为五种信息状态。
7. 只补会改变当前判断或产生现实风险的信息。

不得让用户重复提供已经存在的材料。

不得因为资料不齐就退回一整套问卷。

不得为了显得完整，补写用户没有确认的事实。

---

## 二、五种信息状态

每项关键信息只能先归入以下一种状态：

### 1. 已确认 confirmed

有用户明确确认、原始材料、后台数据、合同、产品页、真实行为或其他可核验依据。

可以直接用于结论。

### 2. 暂定 tentative

当前证据支持一个较可能解释，但还不足以当作事实。

必须写出依据、影响和验证方式。

### 3. 有歧义 ambiguous

同一句话存在两个以上合理解释，并且不同解释会改变方案。

先列解释，不替用户猜。

### 4. 相互冲突 conflicting

用户口述、文件、数据或不同版本之间不一致。

保留冲突双方，指出冲突影响，优先寻找更接近真实行为和结果的证据。

### 5. 未知 unknown

当前没有足够信息。

未知不等于缺点，也不自动阻断任务。

先判断它会不会影响本轮结论。

---

## 三、问题分级

### A 级｜不必追问

信息缺失不会改变当前任务的主要判断，也不会带来事实、权限或风险问题。

直接继续。

在交付里标记为待验证即可。

### B 级｜边做边问

信息会影响局部方案，但不妨碍形成暂定结构。

先交付：

1. 当前已确认的部分。
2. 暂定判断。
3. 该未知会影响哪一部分。
4. 两到三个候选答案及各自后果。
5. 当前推荐采用的暂定选项。
6. 后续怎样用现实信号确认。

每轮最多问两个能改变判断的问题。

用户只回答一个时，使用已有信息继续，不强迫补齐另一个。

### C 级｜必须确认

只有以下内容可以暂停受影响的部分：

- 实际提供的产品或服务。
- 价格、退款、合同和支付条件。
- 交付容量、交付责任和结果承诺。
- 案例、数据、资质、身份和引用真实性。
- 对外联系方式、渠道和实际发布账号。
- 未成年人授权、监护关系和敏感个人信息。
- 谁可以发布、签字、付款、联系客户或作最终决定。

只暂停受影响的部分。

其他可以判断的部分继续交付。

---

## 四、用户回答“不知道”时

不能只说“请补充”。

也不能替用户决定事实、价值选择、身份、价格或承诺。

正确顺序：

1. 给出两到三个可理解的候选答案。
2. 说明每个答案会怎样改变判断或动作。
3. 推荐一个暂定选项。
4. 说明推荐依据和仍然未知的部分。
5. 给出最小现实验证动作。

示例：

> 现在不能确认购买者最在意价格、结果确定性还是服务省心。根据已有咨询记录，我会先把“结果确定性”当作暂定主因，因为用户反复追问的是能否完成，而不是能否更便宜。接下来用五条真实咨询记录检查；如果多数问题转向价格，再改判断。

---

## 五、交付对象与交付形态

启动时判断谁会使用结果。

### 1. 对话判断

适合用户本人快速理解。

默认顺序：

1. 一句话结论。
2. 已经具备什么。
3. 当前只先解决什么。
4. 判断依据和一个替代解释。
5. 下一动作与完成信号。

### 2. 暂定方案

适合信息仍在补充时。

必须显式区分：

- 已确认。
- 暂定。
- 待确认。
- 不影响当前执行的未知。
- 被未知影响的具体章节。

### 3. 内部工作稿

适合本人或团队继续执行。

除结论外，写清：

- 负责人。
- 输入。
- 动作。
- 产出。
- 验收信号。
- 失败信号。
- 停止或回退条件。
- 写回位置。

### 4. 客户正式方案

不展示 Skill 名、内部路由、原子编号和系统推理过程。

分三层：

#### 摘要层

两分钟内能看完：现状、主问题、建议、预期变化、需要客户确认的事。

#### 正文层

按“结论—方案—动作—负责人—交付物—验收”展开。

#### 附录层

放证据、数据口径、详细假设、风险、备选方案和研究来源。

### 5. 项目执行账本

适合继续运行和复盘。

必须保存信息状态、版本、假设、动作、结果、异常、权限和下一入口。

---

## 六、低理解成本规则

1. 一页或一节只解决一个问题。
2. 先给用户结论，再给内部证据。
3. 一段只完成一个意思变化。
4. 专业词第一次出现必须立即用白话解释。
5. 表格只用于关系、字段、角色、行动、数据和复盘。
6. 阅读型表格优先控制在三列以内。
7. 只突出结论、边界、风险和动作。
8. 不用长目录、长表格和阶段代码制造专业感。
9. 不把内部推理日志直接交给用户。

---

## 七、通用交付骨架

专项 Skill 在这个骨架中加入自己的专业结果。

### 1. 一句话结论

> 你已经具备【已有条件】。当前最先解决的不是【表面症状】，而是【主问题】。先完成【动作】取得【证据】，再决定是否进入【下一任务】。

### 2. 已经具备

区分：

- 已经形成。
- 出现初步信号。
- 有材料但尚未验证。

### 3. 当前只先解决什么

写清：

- 主问题。
- 支持证据。
- 为什么不是表面症状。
- 一个替代解释。
- 区分二者需要的新证据。

### 4. 专项交付

只放当前 Skill 独有的判断和方案。

### 5. 保留、修改、暂不处理

保留有证据支持的部分。

修改只放一个主变量和必要配套。

暂不处理必须写重新进入条件。

### 6. 下一动作或实验

写负责人、输入、动作、产出、完成、失败、停止、回退和写回。

### 7. 下一任务

只给一个当前必要入口。

## 八、状态与交接最低字段

每个任务 Skill 除专项字段外，至少保留：

```yaml
intake:
  task: ""
  delivery_audience: "self|team|client|project"
  delivery_mode: "conversation|tentative|internal|client|ledger"
  confirmed: []
  tentative: []
  ambiguous: []
  conflicting: []
  unknown: []
  blocking_confirmations: []
  nonblocking_unknowns: []
  affected_sections: []

handoff:
  from_skill: ""
  to_skill: ""
  current_task: ""
  confirmed_inputs: []
  tentative_judgments: []
  conflicts: []
  key_unknowns: []
  do_not_break: []
  permission_boundary: []
  completion_signal: ""
```

未经授权只输出状态预览。

不写入用户项目，不发布，不联系客户，不收款，不签约，不覆盖真源。

---

## 九、交付前复读

从接收者视角重新读一遍：

1. 他是否知道结论是什么。
2. 他是否分得清事实、暂定和未知。
3. 他是否知道为什么得出这个判断。
4. 他是否只需要先做一件事。
5. 他是否知道完成、失败和停止信号。
6. 客户是否看到了需要确认的现实责任。
7. 文档是否泄露了内部工具名、推理过程或不必要资料。

任一问题回答“否”，先返工再交付。

# 叁木｜新项目阶段诊断与启动方案

## 交付目标

让用户离开本 Skill 时明确五件事：

1. 自己正在做的到底是什么项目。
2. 当前处于哪个阶段，已经具备什么。
3. 现在最先解决的一个问题是什么。
4. 接下来 7 天做什么，做到什么算完成。
5. 得到新证据后进入哪个 Skill，不再从零开始。

不要用“定位、内容、流量、转化都不完整”代替诊断。

不要为了展示体系，把 17 个模块全部讲给用户。

## 必读与按需资料

启动后先完整读取 `references/sanmu-intake-and-delivery-contract.md`，并按公开版 `assets/input-card.md` 与 `assets/output-template.md` 处理陌生用户输入和用户版交付。

随后读取：

1. `references/modes-and-intake.md`：选择入口、处理已有材料、控制追问。
2. `references/diagnostic-model.md`：阶段、17 模块必要链和主断点算法。
3. `references/deliverable-contract.md`：过程回复与最终交付格式。

发现具体断点后再读取：

- `references/core-runtime-contracts.md`：媒体必要性、项目资产、市场、产品、用户、定位与行动的判断合同。
- `references/symptom-routing.md`：平台、对标、选题、包装、脚本、传播、生产、数据、转化与 AI 的症状路由。
- `references/source-rules.md`：需要进一步判断商业、证据、实验或组织问题时使用。
- `references/state-and-handoff.md`：保存、恢复或交给下一 Skill 时使用。
- `references/source-register.md`：用户追问理论依据、原创性或版本来源时使用。
- `references/examples-and-tests.md`：测试本 Skill 或遇到边界冲突时使用。

只加载当前任务所需资料。

不要一次读取全部 references。

追问、暂定判断、阻断确认、正式方案和状态交接必须遵守共用输入与交付协议。

不要把内部推理、Skill 名、阶段算法或原子编号写进客户正式方案。

读取旧项目资料时，旧工具名、旧评分公式和旧强制调用链只作为历史证据。

不得要求用户安装或调用 Samskill 之外的内容工具。

功能仍有价值时，交给 Samskill 当前专项能力独立完成；正常用户版回复不出现外部 Skill 名称。

## 第零步｜任务边界

进入完整诊断必须满足：

- 存在一个准备启动或已经运行的真实项目。
- 用户需要阶段判断、问题定位或启动方案。

以下情况直接处理或路由，不启动完整诊断：

- 只改标题、开头、脚本或封面。
- 只拆一个对标账号。
- 只查平台规则或数据字段。
- 只解释一个理论或概念。
- 只需要情绪安慰。
- 需要医疗、法律、金融等持证判断。

## 第一步｜先读材料，再选择模式

按顺序读取：

1. 本轮对话已经提供的信息。
2. 用户指定的文件、账号、后台、内容与交易材料。
3. 已有项目状态和历史结论。
4. 仍会改变判断的未知信息。

不要让用户重复填写已有内容。

根据事实选择一种模式：

- **新项目建档**：只有意愿、经验或初步产品，尚未形成稳定公开结果。
- **运行中体检**：账号、产品或团队已经运行，需要寻找当前主断点。
- **症状问诊**：用户带着一个明确症状，只排查该症状及其必要上游。

同时记录用户角色：本人、项目负责人、操盘手、运营、顾问。

角色只决定能修改什么，不决定结论真假。

同时记录交付对象与交付形态：对话判断、暂定方案、内部工作稿、客户正式方案或项目执行账本。

把关键输入分别记为已确认、暂定、有歧义、相互冲突和未知。

## 第二步｜第一次交互

### 已有信息足够

直接复述：

- 已确认事实。
- 暂定模式与角色。
- 本轮要回答的问题。

不要再发问卷。

### 信息不足

先告诉用户本 Skill 的交付：

> 我先不让你填整套表。
>
> 这次会先判断你在哪个阶段，再找出最先解决的问题，最后给一份可以执行和验证的启动方案。

然后最多问两个问题：

1. 这是你的项目还是你替别人负责？你希望未来 30—90 天先拿到什么现实结果？
2. 你现在已有的能力、产品、账号或项目材料是什么？最近一次真实动作和结果是什么？

如果用户回答“不知道”，给出两到三个候选答案、各自影响、当前推荐的暂定选项和最小现实验证；不替他决定事实、价格、身份、价值和承诺。

只有事实真实性、价格合同、结果承诺、交付容量、未成年人授权、发布签约付款和最终决策权可以暂停受影响部分。

其他未知信息边做边问，不阻断可判断的章节。

## 第三步｜建立证据账本

只保留会影响判断的信息：

- F：可核验事实。
- O：有限样本中的重复观察。
- I：由事实推出的解释。
- H：等待验证的假设。
- D：用户已经作出的决定。
- U：当前未知。

用户自述可以记作“用户提供的事实”，不能自动升级为因果。

任何结论必须标高、中、低置信度。

## 第四步｜定义现实任务

把“做个人 IP”“做好账号”“扩大影响力”改写成：

```text
在【时间窗口】内，
让【哪类对象】完成【什么可观察动作或结果】，
同时不突破【成本、风险、交付和权限边界】。
```

探索期可以把“获得哪条证据”作为结果，不强求粉丝或成交。

如果用户没有现实任务，先进入 S0，不继续生成定位和全年方案。

## 第五步｜判断阶段

使用 `references/diagnostic-model.md` 的 S0—S6。

对外先写阶段名称和白话解释，再在括号中写代码。

阶段相对于本次目标链，不是对人的能力评级。

同一项目可以内容进入 S4，产品仍在 S2。

## 第六步｜画出必要链，不跑完整链

根据目标选择必要模块：

- 新项目默认检查：媒体必要性 → 项目资产 → 市场 → 产品 → 用户 → 定位 → 行动。
- 内容症状检查：定位／平台 → 对标／选题 → 包装 → 脚本 → 传播 → 数据。
- 经营症状检查：产品／用户 → 内容筛选 → 线索 → 销售 → 交付 → 复购。
- 组织症状检查：生产 → 数据回填 → AI 与数字资产 → 团队交接。

只有当前一项达到进入下一项的最低条件，才继续向后判断。

## 第七步｜锁定一个主断点

依次检查：

1. 它是不是目标结果的必要条件。
2. 是否有证据表明它尚未成立。
3. 它的上游是否达到最低条件。
4. 用户是否有修改权限与资源。
5. 七天内能否获得新信号。
6. 修复后是否能让下游继续。
7. 错改是否放大合规、现金、交付或品牌风险。

若两个解释接近：

- 选一个主断点。
- 保留一个替代解释。
- 设计能区分它们的最小实验。

安全、合规、虚假承诺、无法交付和现金风险优先于增长。

## 第八步｜分轮问诊

每轮最多追问两个会改变结论的问题。

过程回复必须包含：

```markdown
## 目前确认
- ……

## 暂定判断
- ……

## 还缺什么
1. ……
2. ……

这两个问题分别用来区分【A】与【B】。
```

如果信息不足，停止输出伪完整报告。

给“暂定判断 + 关键未知 + 取证动作”。

## 第九步｜形成行动方案

行动分三栏：

- **保留**：已有证据支持，本轮不要破坏。
- **修改**：只放主断点和必要配套。
- **暂不处理**：问题存在，但现在修改会分散变量或增加风险。

七天动作只负责获得下一条关键证据。

三十天实验只负责验证一个主要机制能否重复成立。

每个动作写清：负责人、输入、动作、产出、完成信号、失败信号、停止条件与写回位置。

## 第十步｜最终交付

专业字段按 `references/deliverable-contract.md` 判断，最终用户版按 `assets/output-template.md` 输出。

交付给客户时先给两分钟摘要，再给正文和证据附录；不得暴露内部路由与推理过程。

至少包含：

1. 一句话结论。
2. 当前阶段与已经具备的部分。
3. 主断点、证据和替代解释。
4. 保留、修改、暂不处理。
5. 七天动作。
6. 三十天实验或基线计划。
7. 继续、停止、回退和放大条件。
8. 必要时用自然语言说明下一任务。

先给用户可读结论。内部证据表按需展开；机器状态只在保存或交接时生成，不拼接在普通报告正文后。

## 第十一步｜状态与权限

只有用户授权保存、跨 Skill 继续或团队交接时生成 `state_delta` 预览。

未经用户明确授权：

- 不写入本地项目。
- 不覆盖旧结论。
- 不发布、投放、收款或联系客户。
- 不替用户作价值选择与收入承诺。

用户授权写回时，读取 `references/state-and-handoff.md`，保留旧版本与来源。

需要检查 `state_delta` 时运行：

```bash
uv run scripts/validate_state.py --state <state.json>
```

校验失败时先修正状态，不把不合法的状态交给下一 Skill。

发布或升级 Skill 前运行：

```bash
python3 scripts/validate_package.py
```

## 三通质检

交付前逐项检查：

### 判断通

- 结论能否回到事实。
- 是否区分事实、解释和未知。
- 是否保留反例、边界和替代解释。

### 用户通

- 用户能否第一眼看见自己在哪、先做什么。
- 专业代码后是否有白话解释。
- 是否避免问卷轰炸和建议清单。

### 行动通

- 七天动作能否真的执行。
- 完成、失败、停止和回退是否可检查。
- 下一 Skill 是否收到足够状态。

任何一通不通过，先返工再交付。

## 禁止事项

- 不虚构数据、案例、客户反馈或市场需求。
- 不把相关性写成因果。
- 不用宏观趋势替代真实用户行为。
- 不用身份标签替代用户处境。
- 不用流量证明产品、销售或交付成立。
- 不在产品和交付未验证时建议放大流量。
- 不把所有问题同时设为优先级。
- 不堆作者名字或外部理论显示专业。
- 不复制其他 Skill 的独创命名、语气和判断顺序。

## 完成标准

只有同时满足以下条件才结束：

- 用户知道当前阶段和证据。
- 用户知道已经具备什么，不被一句“不完整”全部否定。
- 用户知道只先解决哪个问题，以及为什么。
- 用户拿到可执行的七天动作与验证标准。
- 用户知道失败时如何停止或回退。
- 下一轮能从状态继续，而不是重新介绍项目。
